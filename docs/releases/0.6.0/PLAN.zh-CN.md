# Muse-CI 0.6：项目、版本、需求与材料归档

项目是长期配置边界；版本是最小交付单元；需求是最小研发单元；节点是最小执行单元。现有版本和需求流程的 ID、SmartDoc、MR 与运行历史保留，不将历史测试流程自动猜测为真实项目。

## 约定与配置

```text
项目目录/
  .muse-project-<项目ID>/
    project.json                 # 唯一项目配置入口，严格 schema
    INDEX.json                   # 根节点与版本索引，派生文件
    skills/                      # 项目技能
    standards/                   # 开发、设计、测试规范
    documents/                   # 长期项目材料
    inputs/ outputs/
    versions/<版本号>/
      version.json               # 版本定义和流程 ID
      INDEX.json                 # 版本根节点与交付物索引
      requirements/              # 需求引用；不复制 Git 仓库
      documents/<文档ID>/rN.sydoc
      nodes/<节点ID>/attempts/N/  # INPUT、RESULT、原始产物
仓库目录/
  .muse/requirements/<需求ID>/
    requirement.json             # 仓库、版本、需求与 MR 的关联
    INDEX.json
    documents/<文档ID>/rN.sydoc
    nodes/<节点ID>/attempts/N/
```

需求执行根是选定 Git 仓库；`.muse/requirements/<ID>` 是该需求在仓库内的材料归档根。同一仓库承载多个需求时分开存放。节点尝试不可变，重跑追加，不覆盖旧输入或输出。版本目录引用需求根，避免在两个地方维护同一份设计稿。SmartDoc 保存原生文件及修订、云端 ID、摘要，JSON 索引不替代文档正文。

配置缺省采用版本化内置约定；显式配置覆盖缺省，不允许未知字段、路径越界或无效配置静默回退。项目可嵌套，但子项目独立配置，不隐式继承父项目权限。服务只访问已配置的受信工作区，仓库由项目配置声明；插件不提交任意绝对路径执行命令。

## 交互

- 顶部依次选择项目与版本；项目切换后清除旧版本和需求上下文，禁止混用旧节点操作。
- 左侧固定展示当前版本核心交付物：版本定义、产品稿、视觉稿、架构方案、测试与 MR。文档直接打开原生 SmartDoc，MR 进入对应需求审查。
- 手机通过“项目与版本”和“交付物”抽屉访问同一导航，不用横向缩小整个 Desktop 侧栏。
- 主流程只展示版本；需求列表进入独立画布。明确显示所属项目、版本、仓库与归档状态。
- 新项目从受信工作区导入/初始化约定目录；新版本使用项目缺省；新需求选择项目已声明仓库。未归属历史流程在单独迁移入口显式关联，不按标题猜测。

## 实施与验收

1. 静态项目合同、约定目录、严格配置解析及父子项目边界。
2. 项目注册、版本关联、需求仓库关联与历史兼容。
3. 原生文档、固定输入、节点尝试和 MR 的持久归档；失败保留待重试状态。
4. 项目/版本选择与交付物导航，两端共用业务 UI。
5. Muse-CI 自身创建 0.6 版本及子需求，写入 PRD、设计、方案与用例；现有 0.4/0.5 明确关联到长期项目。
6. 自动验证配置、权限、路径/符号链接、幂等、历史归档、导航上下文切换。
7. 国内生产账号、既有公网中转、连接的 Find N6：项目切换、版本选择、需求进入、原生交付物与实际节点/产物操作。设备结果独立留痕，不将单元测试当真机通过。

正式发布与 MR 合并仍遵循原有门禁。本轮允许建立研发版本，不用人工标过代替真实执行。
